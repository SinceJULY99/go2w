## 1. 项目目标与当前进度

**目标**：在 Unitree Go2W 上实现基于 Livox MID360 激光雷达的自主导航，分三步走：

1. 二维几何导航：建图 → 定位 → 规划和避障 → 控制机器人行走（**当前阶段**）
2. 语义地图：加入视觉，识别物体
3. 具身导航：理解自然语言指令，比如"去冰箱旁边"

**背景**：项目原有一套"三机"系统（PC2 跑雷达驱动，Orin 跑 FAST-LIO，外部 Ubuntu 跑定位）。这套系统建出来的地图是歪的，定位要经过 Wi-Fi、延迟约 2 秒，重启后恢复要手动开十几个终端，一直没能实现自主行走。经过评估，决定**在 Orin 上重建一套单机系统**，旧系统保留作回退。

**进度**（按阶段验收）：

| 阶段 | 内容 | 状态 |
|---|---|---|
| S0 | 设备摸底、网络和时间修复 | ✅ |
| S1 | Docker 化的 ROS 2 Humble 环境 | ✅ |
| S2 | 雷达接入 Orin、坐标系、外参标定 | ✅ |
| S3 | 激光惯性里程计 + 平面里程计 | ✅ |
| S4 | 建图 | ✅ |
| S5 | 定位 | ✅ |
| S6 | 速度桥（ROS → Go2W 运动指令） | ✅ |
| S7 | Nav2 自主导航 | 🔶 首轮 3 个目标成功，持续测试中 |

## 3. 网络架构

### 3.1 两个网段

| 网段 | 用途 | 成员 |
|---|---|---|
| `192.168.1.0/24`（Wi-Fi，Mesh 路由器 YanGu_5G） | 开发和远程可视化 | Mac、Ubuntu `.167`、Orin `.111`、PC2 `.142` |
| `192.168.123.0/24`（Go2W 内部交换机，有线） | 机器人内部通信 | 主控 `.161`、PC2 `.18`、Orin `.222` |

### 3.2 一个特殊情况：雷达的 IP 和 Wi-Fi 在同一网段

MID360 的地址是 `192.168.1.194`，物理上接在 Go2W **内部交换机**上，但 IP 却和 **Wi-Fi 网段**重叠。如果直接给有线口配 `192.168.1.x/24`，就会和 Wi-Fi 的路由冲突。

**解决办法**（沿用 PC2 原来的做法）：
- 在 Orin 有线口上额外挂一个 `192.168.1.51/32`（只有这一个地址，不代表整个网段）；
- 加一条只通往雷达的主机路由：`192.168.1.194/32 dev enP7p1s0 src 192.168.1.51`；
- 去往 `/32` 主机的路由比去往 `/24` 网段的更具体，所以只有发给雷达的流量会走有线，其余 `192.168.1.x` 的流量照常走 Wi-Fi。

这样做的好处是**不需要改雷达本身的配置**，随时可以撤销。脚本：`scripts/orin/setup-lidar-net.sh`，用 NetworkManager 持久化。

**限制**：雷达的数据是单播发给 host IP 的，所以**同一时间只能有一台机器运行驱动**（Orin 是 `.51`，PC2 是 `.50`）。

### 3.3 Orin 的网卡

| 网卡 | 地址 | 用途 |
|---|---|---|
| `wlP1p1s0` | `192.168.1.111` | Wi-Fi：SSH、远程可视化 |
| `enP7p1s0` | `192.168.123.222/24` + `192.168.1.51/32` | 有线：雷达数据、Go2W 运动指令 |
| `l4tbr0` | `192.168.55.1` | USB-C 设备模式：Wi-Fi 不通时的救命通道 |
| `enP8p1s0` | 未使用 | 备用 |

### 3.4 三条登录通道

| 通道 | 命令 | 什么时候用 |
|---|---|---|
| Wi-Fi | `ssh w@192.168.1.111` | 平时 |
| 经 PC2 走有线 | `ssh -o HostKeyAlias=192.168.1.111 -J unitree@192.168.1.142 w@192.168.123.222` | Orin 的 Wi-Fi 掉线时（今天实际用到过） |
| USB-C 线 | `ssh w@192.168.55.1` | 网络配置出错时 |

Mac 到 Orin 和 PC2 都配置了免密登录（ed25519 密钥，存在 macOS 钥匙串里）。

这些问题都是在摸底时发现并修复的，属于"地基"。

| 问题 | 现象 | 原因 | 处理 | 效果 |
|---|---|---|---|---|
| Wi-Fi 延迟高 | ping 80–130 ms，旧系统 RViz 卡顿 | Orin 无线网卡开着省电模式 | `nmcli ... 802-11-wireless.powersave 2`（永久生效） | ping 降到平均 12 ms |

| docker 每次都要 sudo | — | 用户不在 docker 组 | `usermod -aG docker w` | — |
| 时区错误 | 时区为 AKDT（阿拉斯加） | — | 改为北京时间 | — |

## 5. 软件环境

### 5.1 为什么用 Docker

Orin 的宿主系统是 **Ubuntu 24.04**，官方只提供 ROS 2 Jazzy；而 Unitree 和 Livox 的生态、外部 Ubuntu 用的都是 **Humble**。Jazzy 和 Humble 之间的 DDS 互通没有官方保证，旧系统 Foxy 和 Humble 混用就吃过亏。所以宿主机保持干净，**ROS 全部放进一个 Humble 容器**。

### 5.2 镜像 `go2w-humble:dev`（4.57 GB）

| 层 | 内容 |
|---|---|
| 基础镜像 | `ros:humble-ros-base`（Orin 访问不了 Docker Hub，经 `docker.m.daocloud.io` 拉取） |
| apt 源 | 换成清华镜像（Ubuntu ports 和 ROS 2 都换） |
| ROS 包 | CycloneDDS、PCL、pointcloud_to_laserscan、robot_state_publisher、xacro、tf2、slam_toolbox、**Navigation2**、foxglove_bridge、rosbag2（mcap）、teleop、**domain_bridge** |
| Livox-SDK2 | 构建镜像时从源码编译安装 |

### 5.3 第三方源码

Orin 和 Mac 访问 GitHub 都不稳定，所以从旧容器 `go2w_foxy` 里**直接复制了带完整 git 历史的源码**，版本记录在 `third_party.lock`：

| 源码 | 版本 | 说明 |
|---|---|---|
| Livox-SDK2 | `08f523c` | 编进镜像 |
| livox_ros_driver2 | `4a1def9` | 和 PC2 上用的是同一份 |
| FAST_LIO_ROS2（Ericsii） | `2fffc57` | 旧容器里有两处为 Foxy 做的改动，Humble 下不需要，已还原成上游版本 |

### 5.4 容器

| 容器 | 作用 | 启动方式 |
|---|---|---|
| `go2w_humble` | 导航核心（交互开发、运行各阶段 launch） | `docker compose`，开机自启 |
| `go2w_viz_bridge` | 可视化桥（第 15 节） | 同上，独立运行，出问题不影响导航核心 |
| `go2w_foxy` | 旧系统，保留作回退 | 原样保留 |

两个新容器都使用 host 网络（雷达走原始 UDP），仓库目录挂载到容器内的 `/go2w`。

### 5.5 代码仓库与开发流程

- 代码只有一份，在 Mac 的 `~/Desktop/go2w/`（git）；`scripts/sync.sh` 用 rsync 同步到 Orin 的 `~/go2w/`。Wi-Fi 不通时，它会自动改走 PC2 有线跳板。
- 第三方源码、编译产物、地图、录包只放在 Orin 上，不进 git，同步时也不会被删除。
- 容器内用 `scripts/build.sh` 调用 colcon 编译（symlink-install，改 Python 和参数文件不用重新编译）。
- 自己写的 ROS 包：`go2w_bringup`（launch、参数、URDF、节点）和 `unitree_api`（Go2W 指令消息）。

## 7. 雷达驱动

- 节点：`livox_ros_driver2`，运行在 Orin 容器里（`lidar.launch.py`）。
- 配置：`config/MID360_config.json`，是 PC2 原配置的副本，只把 host IP 从 `.50` 改成了 `.51`。PC2 上 Unitree 的原配置没有动。
- 输出格式：`xfer_format: 1`（Livox CustomMsg，FAST-LIO 需要这种格式），坐标系 `livox_frame`。
- 话题：`/livox/lidar`（10 Hz）、`/livox/imu`（200 Hz）。
- CPU：在 Orin 上约 50–60%；同样的驱动在 PC2 上要 206%。

**关于配置里的外参**：Unitree 原配置写的是 `pitch 90°, yaw 180°`，驱动会把它写进雷达硬件。一开始怀疑它只旋转了点云、没有旋转 IMU，导致两者错位。实测（第 9 节）证明，点云中的地面法向量和 IMU 测到的重力方向只差约 1°，**两者在同一坐标系**，所以保留原值不动。

## 8. 坐标系设计

### 8.1 坐标树

```
map ──(AMCL 或 slam_toolbox)──▶ odom ──(planar_odom：x, y, yaw)──▶ base_footprint
    ──(planar_odom：机身实时 roll, pitch)──▶ base_link
    ──(URDF 静态：雷达外参)──▶ livox_frame
    ──(URDF 静态：IMU 偏移)──▶ body
```

| 坐标系 | 含义 | 发布者 |
|---|---|---|
| `map` | 地图坐标系 | — |
| `odom` | 里程计原点：启动时机器人所在位置，水平 | AMCL / slam_toolbox 发布 `map → odom` |
| `base_footprint` | 地面上、旋转中心正下方，**z=0 就是地面**，只有 yaw | `planar_odom` |
| `base_link` | 机身，带实时俯仰和横滚 | `planar_odom` |
| `livox_frame` | 雷达点云坐标系 | `robot_state_publisher`（URDF） |
| `body` | MID360 内置 IMU（FAST-LIO 的名字，代码里写死了） | URDF |

### 8.2 为什么这样设计

- 旧系统直接用 FAST-LIO 的 `camera_init → body`。这两个坐标系都是**雷达 IMU 的坐标系，跟着雷达倾斜 15.6°**，并不对齐地面。在倾斜的坐标系里切 2D 激光，就会把前方地面切进来、远处只切到墙的高处，**这是旧地图偏斜、出现双线的主要原因**。
- 新设计中，`base_footprint` 贴着地面且水平，2D 切片、AMCL、Nav2 全部在这个坐标系下工作。
- FAST-LIO 自己发布的 `camera_init → body` 被重定向到 `/fast_lio/tf`，不进入全局 TF，避免出现两棵互不相连的坐标树。

## 9. 雷达外参标定

### 9.1 静态标定：倾角和高度

**工具**：`scripts/calib/mid360_static_check.py`

**方法**：机器人在平地上静止，录几秒点云和 IMU 数据：
1. IMU 加速度的平均值给出重力方向；
2. 用 RANSAC 依次从点云中提取最大的几个平面，按法向量区分地面、天花板和墙；
3. 地面平面的法向量给出倾角，平面到原点的距离就是雷达离地高度；
4. 比较地面法向量和 IMU 重力方向，判断点云和 IMU 是否在同一坐标系。

**过程**：
| 轮次 | 依据 | pitch | roll | 高度 | 验收：地面倾斜 / 高度误差 |
|---|---|---|---|---|---|
| 第 1 次 | IMU 重力方向 | 16.3° | −3.0° | 0.54 m | 1.35° / −1.7 cm ❌ |
| 第 2 次 | **地面平面** | **15.59°** | **−1.80°** | **0.527 m** | **0.24° / −0.3 cm** ✅ |
| 复核 | 地面平面 | 15.43° | −1.99° | 0.525 m | 已收敛，差异约 0.2°，属于测量噪声 |

**结论**：IMU 重力方向和地面之间有约 1.4° 的差异（原因不明，可能是 IMU 零偏，也可能是地板有坡度）。**2D 导航以地面为准**，所以最终采用以地面为基准的结果。

另外两个发现：
- 0.5 m 以内没有任何点，**保护架在雷达盲区里**，不会被当成障碍物；
- 历史上手动试过的 10°、11.5°、13° 都偏小，实际倾角约 15.6°。

### 9.2 动态标定：偏航角和水平位置

**工具**：`scripts/calib/odom_motion_check.py`（分析录包，自动把轨迹切成直线、原地转圈、绕圈几种运动段）

| 测试 | 方法 | 结果 | 结论 |
|---|---|---|---|
| 直行 | 两次直行 3 m | 运动方向偏离雷达 x 轴 **+3.3°、+3.4°** | 雷达偏航 **−3.4°** |
| 原地转圈 | 原地转 357° | 轨迹圆半径 0.190 m，旋转中心在雷达正下方点后方 0.188 m，逐帧标准差 2.6 cm | 雷达在旋转中心**前方 0.187 m、右侧 0.017 m** |

**验证**：修正后，绕圈测试中的直线段方向偏差接近 0°（修正前是 3.4°）；原地转 15° 时，机身前后只挪了 1.2 cm。

### 9.3 最终外参（写在 `urdf/go2w.urdf.xacro`）

```
base_link → livox_frame:  xyz = (0.187, -0.017, 0.527)  rpy = (-1.80°, 15.59°, -3.4°)
livox_frame → body(IMU):  xyz = (0.011, 0.02329, -0.04412)   （Livox 官方值）
```

## 10. 激光惯性里程计（FAST-LIO）

**作用**：把雷达点云和 IMU 紧耦合融合（迭代误差状态卡尔曼滤波 + ikd-Tree 地图），输出高精度的 3D 位姿，同时输出去除了运动畸变的点云。

**配置**（`config/fast_lio_mid360.yaml`，基于上游 `mid360.yaml` 修改）：

| 参数 | 值 | 说明 |
|---|---|---|
| `extrinsic_est_en` | **false** | 上游默认开启在线估计外参。MID360 内置 IMU 的外参是固定的，关掉更稳定 |
| `extrinsic_T` | (−0.011, −0.02329, 0.04412) | 雷达在 IMU 坐标系中的位置（Livox 官方值） |
| `extrinsic_R` | 单位阵 | 已实测确认点云和 IMU 方向一致 |
| `blind` | 0.5 m | 滤掉机身和保护架附近的点 |
| `point_filter_num` | 3 | 每 3 个点取 1 个 |
| `filter_size_surf` / `filter_size_map` | 0.5 m | 降采样分辨率 |
| `map_en` / `path_en` / `pcd_save_en` | false | 关掉累积地图、轨迹和 PCD 保存，避免长时间运行时内存增长 |
| TF | 重定向到 `/fast_lio/tf` | 不进入全局 TF 树 |

**输出**：`/Odometry`（`camera_init → body`，10 Hz）、`/cloud_registered_body`（IMU 系下去畸变后的点云，10 Hz）。

**性能**：CPU 约 25–30%；静止时 2 分钟内的漂移小于 5 mm；**绕场 13 m 回到原点，误差 1.8 cm，航向误差 0.2°**。

**局限**：雷达数据一旦中断，FAST-LIO 只能靠 IMU 推算，几秒内就会漂出一米多，而且恢复数据后也不会自动纠正（第 19 节有实际案例）。

## 11. 平面里程计与健康监测

**节点**：`scripts/planar_odom.py`（自己写的）

### 11.1 位姿换算

FAST-LIO 输出的是 IMU（`body`）在它自己的初始坐标系中的位姿 `T_f`。启动时 `T_f` 为单位阵，所以机身相对启动时刻的位姿是：

```
T_odom_base(t) = T_base_body · T_f(t) · T_base_body⁻¹
```

其中 `T_base_body` 是 URDF 里的静态外参，从 TF 读取。因为 `base_link` 已经按地面校平，`odom` 天然就是水平的。

然后把旋转分解成 `R = Rz(yaw) · R_tilt`：
- **`odom → base_footprint`**：只保留 x、y、yaw，供 2D 建图、定位和 Nav2 使用；
- **`base_footprint → base_link`**：`R_tilt`，也就是机身实时的俯仰和横滚；
- z 方向的漂移不发布（平面导航用不到，实测 3D 高度漂移可达几厘米到二十几厘米）。

**为什么要单独保留俯仰和横滚**：最早的版本把俯仰和横滚直接丢掉了。Go2W 加减速时机身会前后晃动，哪怕只倾斜 3°，1.5 m 外的地面在计算中就会被"抬高" 8 cm，被当成障碍物。保留实时姿态后，点云会按机身的真实姿态变换，这个问题就没有了（第 19 节）。

### 11.2 输出

| 输出 | 内容 |
|---|---|
| TF `odom → base_footprint` | 平面位姿 |
| TF `base_footprint → base_link` | 机身俯仰和横滚 |
| `/odom` | 平面位姿 + 速度（差分后做一阶低通，系数 0.5；速度在机身坐标系下） |
| `/odom_healthy` | 健康状态，10 Hz |

### 11.3 健康监测（安全关键）

- FAST-LIO 的输出**中断超过 0.5 s**，就判定为不健康，并且**一直保持不健康**，直到重启。
- 不健康之后，**停止发布 `/odom` 和所有 TF**。下游的 slam_toolbox、AMCL、Nav2 拿不到新的坐标变换，会自动停下来，而不是接着吃错误的位姿。
- 速度桥收到"不健康"后，立即停车并上锁（第 16 节）。

**为什么锁定、不自动恢复**：实测网线断开 25 s 后，FAST-LIO 恢复数据时已经彻底发散（位置跑到几千公里外），这时候继续用一定是错的。

**验证**：暂停雷达驱动 2 s 来模拟中断，0.6 s 内判定为不健康，odom 停止输出；**在真实导航中也触发过一次**，速度桥正确停车并上锁。

|---|---|---|
| 运动模型 | **`OmniMotionModel`（全向）** | 见下文 |

**为什么用全向模型**：第一次用的是差速模型，在倒车转向的过程中，不确定度在 1 秒内从 ±0.1 m / ±7° 暴涨到 ±1.1 m / ±84°，定位丢失。录包分析发现，**Go2W 运动时横向速度最高能到 0.52 m/s**，有些时段几乎是纯横移。差速模型假设机器人不会横着走，只能把横移解释成"先猛转 90° 再前进"，往航向里加了很大的噪声，粒子就散开了。换成全向模型后，同样的工况全程稳定。

**测试结果**（230 s，包括 17 s 倒车、最快 0.52 m/s 的横移、最快 60°/s 的转向）：

| 项目 | 结果 |
|---|---|
| 收敛 | 从 ±0.5 m / ±15° 开始，走十几秒后收敛到 ±0.13 m |
| 收敛后的不确定度 | 全程 ≤ 0.2 m / 7.6° |
| scan 与地图的贴合率 | 89–96% |

**检查工具**：`scripts/calib/loc_check.py`，每秒打印 AMCL 的位姿、不确定度，以及"贴合率"（激光点落在地图障碍物 15 cm 以内的比例）。

## 15. 远程可视化

**需求**：在外部 Ubuntu 上用 RViz 看地图、scan 和机器人位置，并能设置初始位姿、发导航目标。

**旧方案的问题**：4 个自写的 TCP 转发脚本，加上两套 DDS 配置（其中一套放在 `/tmp`，重启就会丢）。定位本身也依赖这条 Wi-Fi 链路。

**新方案**：
- Orin 上单独运行一个容器 `go2w_viz_bridge`，用 ROS 官方的 `domain_bridge`，在域 43 和域 44 之间按白名单转发话题（`config/viz_bridge.yaml`）：
  - 机器人 → RViz：`/map`、`/scan`、`/tf`、`/tf_static`、`/odom`、`/odom_healthy`、`/robot_description`、`/amcl_pose`、`/plan`、局部和全局代价地图、机器人轮廓、速度桥的上锁状态；
  - RViz → 机器人：`/initialpose`（2D Pose Estimate）、`/goal_pose`（2D Goal Pose）。
- Ubuntu 端（`scripts/ubuntu/`）：`go2w_rviz.sh` 一键设置环境（域 44 + 专用的 DDS 配置）并打开 RViz；`go2w.rviz` 是预设好的显示配置，俯视视角，包含地图、scan、代价地图、路径和机器人轮廓。
- 实测：经 Wi-Fi 收到的 `/scan` 是 9.96 Hz，基本没有损耗。

**设计要点**：Wi-Fi 断了，只是画面不更新，机器人照常定位和导航。桥是一个单独的容器，挂了也不会影响导航核心。

## 16. 运动控制：速度桥

### 16.1 和 Go2W 通信

- 查看 Orin 上 Unitree 的官方 SDK（`unitree_sdk2`，2026-07-09，带 Go2W 示例）得知：Go2W 用的是标准的 sport 接口，`Move(vx, vy, vyaw)` 的 API ID 是 1008，`StopMove` 是 1003。**调用一次 Move，机器人会走 1 秒然后自动停下**，要持续运动就得不断调用。
- 没有直接链接 C++ SDK：SDK 自带一份 CycloneDDS 库，和 ROS 用的那份放进同一个进程可能冲突。改成**纯 ROS 2 的做法**：
  - 照着 SDK 头文件里的 IDL 定义，逐个字段写出 `unitree_api` 消息包（`Request`、`RequestHeader`、`RequestIdentity`、`RequestLease`、`RequestPolicy`、`Response` 等）。ROS 2 会把它映射成 DDS 类型 `unitree_api::msg::dds_::Request_`，和 Go2W 主控完全一致；
  - 往话题 `/api/sport/request`（对应 DDS 话题 `rt/api/sport/request`）发请求，从 `/api/sport/response` 收回复。
- 验证：`scripts/calib/sport_api_probe.py` 发 StopMove 和 GetState，主控都回复 `code=0`，状态里能看到 `gait=1`、`speedLevel=0`。

### 16.2 速度桥节点 `go2w_cmd_bridge.py`

- **一个进程同时连两个 DDS 域**（rclpy 的两个 Context）：
  - 域 43：订阅 `/cmd_vel`、`/odom_healthy`，提供 `~/arm` 服务（上锁/解锁）；
  - 域 0：以 20 Hz 发布 Move（参数是 JSON：`{"x": vx, "y": vy, "z": wz}`），需要时发 StopMove。
- 自己接管 SIGINT 和 SIGTERM 信号，保证退出前一定会发出停车指令。

### 16.3 六层安全保护

| 层级 | 机制 | 参数 |
|---|---|---|
| 1 | **启动后默认上锁**，必须调用 `~/arm` 解锁；解锁前收到的指令一律作废 | — |
| 2 | 限速 | 前后 0.45 m/s，横向 0.1 m/s，转向 0.8 rad/s（约 46°/s；10-22 由 0.3 m/s、0.2 m/s、30°/s 调整） |
| 3 | 指令超时就停车 | 0.3 s |
| 4 | **里程计不健康就停车并上锁**；不健康时拒绝解锁 | `/odom_healthy` 为 false，或超过 0.5 s 收不到 |
| 5 | 程序退出时连发 3 次 StopMove | — |
| 6 | Go2W 自身的保护 | 1 s 收不到 Move 就自动停 |

### 16.4 实测（`scripts/calib/cmd_step_test.py`，脚本本身也有更严的限速：≤ 0.15 m/s、≤ 20°/s、≤ 2 s）

| 测试 | 期望 | 实测 |
|---|---|---|
| 前进 0.1 m/s，持续 1 s | 0.100 m | **0.100 m**，横向 1 mm，转角 0.3° |
| 左转 15°/s，持续 1 s | +15° | **+16.0°**，方向正确，平移 1.2 cm |
| 行驶中模拟里程计中断 | 停车并上锁 | **故障发生后 0.63 s 停车并上锁**，之后的指令全部被忽略 |
| 上锁时发 `/cmd_vel` | 不动 | 没有发出任何 Move |
| 停车延迟（最后一条指令 → odom 速度归零） | — | 0.8–1.0 s（0.3 s 超时 + 约 0.2 s 滤波滞后 + 约 0.3 s 实际减速） |

| 10 | 断网后 FAST-LIO 发散，slam_toolbox 内存爆掉（10 GB） | 日志 | 中断期间只靠 IMU 推算；下游照单全收错误数据 | 健康监测 + 不健康时停止发布 TF |
| 11 | 差速模型 AMCL 在倒车转向时丢定位 | `loc_check` + 录包分析 | Go2W 会横移 | 改用全向模型 |

## 20. 遗留问题与下一步

### 20.1 遗留问题（按严重程度）

| # | 问题 | 影响 | 可能的方向 |
|---|---|---|---|
| 1 | **网线在运动中断开** | 一断就得重启整套系统、重新设位姿 | 把 Orin 固定在机身上、用短线和带锁扣的接头、做好线缆固定 |
| 2 | 里程计中断后不能自动恢复 | 同上 | 自动重启 FAST-LIO；基于 3D 地图重定位 |
| 3 | 初始位姿要手动给 | 每次启动都要人工操作 | 固定停车点、记住上次位置、3D 重定位 |
| 4 | 2D 定位依赖家具 | 家具多的房间里贴合率约 75%，家具挪动后会下降 | 提高切片下限，或者改用 3D 点云地图定位 |
| 5 | 近处低矮障碍物看不到 | 前方 0.5 m 处只能看到 0.32 m 以上，后方 0.5 m 处只能看到 0.6 m 以上（按安装角度计算） | 加深度相机，或接入 Go2W 自带的避障 |
| 6 | 代价地图噪点修复后，还没在长时间运动中验证 | — | 继续测试 |
| 7 | 机器人轮廓是估计值 | 影响避障余量 | 实测 |
| 8 | Ubuntu 的 IP 写死在配置里，没有做地址保留 | IP 一变就看不到画面 | 在路由器上做 DHCP 保留 |
| 9 | 导航程序要手动启动 | — | S7 通过后做成开机自启 |
| 10 | RTC 断电后丢时间 | 没有外网时多台设备的时间可能不一致 | 装纽扣电池；让 Orin 当局域网时间服务器 |

### 20.2 下一步

1. **处理网线**（前提条件）；
2. 继续 S7：长路线、多目标点、绕开临时障碍；分析 `s7_nav1_114954` 录包；
3. 运动中验证代价地图不再累积噪点；
4. 评估 3D 定位方案（同时解决遗留问题 2、3、4）；
5. 导航程序开机自启，完善健康检查；
6. 几何导航稳定后，进入语义地图和具身导航阶段：加 RGB-D 相机（Orin 载板有 GMSL 接口）→ 开放词汇检测 + 语义地图 → 用大模型把语言指令转成导航目标。原则是：**大模型决定"去哪里"，Nav2 负责"怎么去"**。
